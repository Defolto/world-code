# Техническая архитектура

Документ-спутник к «Общая идея проекта». Здесь — как устроен продукт внутри: исполнение кода, симуляция мира, формат уровней, персонаж и конвейер контента.

Дата: 10 сентября 2026.

---

## 1. Главный принцип

Код ученика не управляет анимацией. Он выполняется целиком за несколько миллисекунд и оставляет после себя **лог кадров** — запись того, что произошло. Всё остальное (анимация, перемотка, медали, проверка в CI) работает с этим логом, а не с живым интерпретатором.

Отсюда следуют три свойства, заявленные в общей идее:

- **Детерминизм.** Один и тот же код на одном сиде даёт побайтово одинаковый лог.
- **Перемотка.** Шаг назад — это `frames[i-1]`, а не откат состояния мира.
- **Автосолвер в CI.** Тот же прогон запускается без браузера, обычным CPython.

Формально прогон — чистая функция:

```python
run(source, level, seed, loadout) -> FrameLog
```

Второй прогон на нулевых статах (для медалей) — это тот же вызов с `loadout=EMPTY`. Не отдельный режим, не флаг в симуляторе, а другое значение аргумента.

## 2. Слои

```
Редактор (CodeMirror, браузер)
        ↓ исходник
Web worker
    ├── Pyodide — настоящий CPython в wasm, код ученика
    └── Симулятор — правила мира, на Python
        ↓ лог кадров (JSON)
Плеер и рендер (SVG, главный поток)
```

**Симулятор написан на Python и существует в одном экземпляре.** В браузере он крутится внутри Pyodide рядом с кодом ученика — значит `hero.move_right()` это обычный синхронный вызов, без мостов через `Atomics` и `SharedArrayBuffer`, без COOP/COEP-заголовков. В CI тот же модуль запускается обычным CPython под pytest.

Рендер не знает правил игры. Он чистая функция от кадра, и его можно заменить целиком, ничего не сломав.

Всё исполнение живёт в веб-воркере: Pyodide (~7 МБ, кэшируется) грузится на входе в урок, пока ребёнок читает условие; зависший код убивается терминацией воркера, главный поток не блокируется.

## 3. Формат лога кадров

### Шапка

```json
{
  "version": 1,
  "level": "forest-03",
  "seed": 148223,
  "loadout": {"strength": 0, "agility": 0, "stamina": 0, "items": []},
  "outcome": {"status": "win", "reason": null},
  "metrics": {"ticks": 42, "lines": 118, "ast_nodes": 34, "repeats": 0},
  "checksum": "a3f9...",
  "frames": [],
  "error": null
}
```

`status` — `win` | `lose` | `timeout` | `error`.
`checksum` — хэш кадров. В CI ловит регрессии: «тот же код на том же сиде дал другую плёнку» значит кто-то сломал детерминизм.

### Кадр

```json
{
  "i": 12,
  "tick": 7,
  "line": 4,
  "world": {},
  "events": [
    {"type": "attack", "who": "hero", "target": "goblin-1", "damage": 5},
    {"type": "death", "who": "goblin-1"}
  ],
  "vars": {"i": 2, "enemies_left": 1}
}
```

**`world` присутствует не в каждом кадре.** Строка `x = 5` даёт кадр с `line`, но мир не изменился — снимок не пишется. Плеер один раз строит индекс «ближайший предыдущий снимок для кадра i», перемотка остаётся мгновенной, а лог не раздувается на пятидесяти тысячах выполненных строк.

**`vars`** — значения переменных верхнего фрейма, их отдаёт `sys.settrace` даром. Пишем только числа, строки, булевы и короткие списки. Это превращает пошаговый режим в настоящий отладчик: видно, как `i` растёт по циклу.

### Снимок мира

```json
{
  "hero": {"x": 3, "y": 5, "dir": "right", "hp": 18, "hp_max": 20,
           "energy": 6, "energy_max": 10, "coins": 2},
  "units": [{"id": "goblin-1", "kind": "goblin", "x": 6, "y": 5,
             "hp": 8, "hp_max": 8, "state": "idle"}],
  "items": [{"id": "coin-1", "kind": "coin", "x": 8, "y": 2, "taken": false}],
  "tiles": []
}
```

`tiles` — клетки, которые меняют состояние по ходу уровня (ворота; позже — открытая дверь, нажатая кнопка). Статичная карта живёт в файле уровня. Пока таких клеток единицы, в снимок идут все, а не только изменившиеся: любой кадр рисуется без поиска предыдущего снимка.

### Почему нужны и снимок, и события

Снимок даёт перемотку в любую точку. События дают анимацию и текстовый лог. Из `{"type":"move","from":[3,5],"to":[4,5]}` рендер интерполирует шаг; из снимка он бы только телепортировал персонажа.

Типы событий: `move`, `wait`, `attack`, `damage`, `death`, `pickup`, `blocked`, `no_energy`, `spotted`, `lost`, `say` (это `print()` ученика), `level_end`.

`no_energy` обязано быть событием, а не дыркой в тиках: иначе ребёнок не поймёт, почему герой замер, и решит, что игра сломалась.

### Два таймлайна

Строка кода и тик мира — не одно и то же. `x = 5` не стоит ничего, `hero.attack()` стоит три тика, проверка условия `while` — строка без тика. Каждое событие помечено парой `(tick, line)`, и плеер из одних данных даёт два режима: **по тикам** (анимация мира) и **по строкам** (отладчик).

## 4. Формат уровня

Система координат: `[x, y]`, начало в левом верхнем углу, `y` растёт вниз. Зафиксировать один раз и написать комментарием в каждом файле.

```yaml
id: forest-03
lesson: 5
title: Лес гоблинов
brief: Гоблин стоит на дороге. Бей, пока он жив, потом иди к сундуку.

map:
  legend:
    "#": wall
    ".": floor
    "@": hero
    "g": goblin
    "$": chest
  grid: |
    ##########
    #@..g....#
    #.####...#
    #......$.#
    ##########

units:
  goblin: {hp: 8, damage: 2, attacks_every: 3, sight: 3, on_spot: chase}

api:
  - hero.move_right
  - hero.move_up
  - hero.attack
  - hero.nearest_enemy

starter: |
  # Гоблин мешает пройти
  hero.move_right()

solution: |
  while hero.nearest_enemy():
      hero.attack(hero.nearest_enemy())
  hero.move_right()
  hero.move_right()

goals:
  - reach: [7, 3]
  - stay_alive: true

medals:
  short: auto        # порог считается от эталона
  clean: no_repeat

hints:
  - after_fails: 2
    text: Что случится, если гоблин ещё жив, а ты уже пошёл дальше?
```

**Позиции в сетке, характеристики в `units`.** Методист видит карту глазами, а числа правит в структурированном месте.

**`api` — не запрет синтаксиса, а список доступных методов.** Ученику никто не мешает написать `for` раньше срока. Список наполняет боковой справочник и даёт человеческую ошибку на `hero.fly()` вместо `AttributeError`.

**`short: auto`** — порог считается как `ast_nodes(solution) × 1.3`. Руками пороги для трёхсот уровней никто не подберёт, а при генерации через LLM это ещё и лишний параметр для галлюцинаций.

**`solution` не уезжает в браузер.** Бэкенд отдаёт уровень с вырезанным решением и невыданными подсказками. Исполнение клиентское, раздача контента серверная.

### Генератор (с занятия 9)

```yaml
generator:
  size: [10, 5]
  enemies: {count: [2, 4], kinds: [goblin]}
  guarantee: [path_exists, solvable_by_reference, solvable_at_zero_stats]
  seeds_to_pass: 3
```

CI прогоняет эталонное решение по сотне сидов. Не прошло хоть на одном — сборка падает. Это и есть автосолвер как гейт качества; без него генерация уровней через LLM выдаёт нерешаемые карты, и вы узнаёте об этом от ребёнка.

`solvable_at_zero_stats` — вторая обязательная гарантия: если уровень требует прокачки, нарушены сразу два правила общей идеи («школа не открывает силу», «прокачка не влияет на оценку»).

### Валидация

Pydantic-модель на YAML, `unknown keys` — ошибка. Когда файлы пишет LLM, опечатка `attacks_evry` иначе молча даёт гоблина, который никогда не бьёт, и уровень тихо становится тривиальным.

## 5. Объекты и взаимодействие

Всё на карте — одна модель с флагами, а не отдельные классы:

```yaml
objects:
  wall:   {blocking: true, blocks_sight: false}
  chest:  {blocking: true, interactive: [open], gives: coins}
  door:   {blocking: true, interactive: [open], opens_with: key}
  lever:  {blocking: false, interactive: [pull], toggles: door-1}
  key:    {blocking: false, pickable: true}
  spikes: {blocking: false, damage: 3}
  gate:   {waits_to_open: 2}
```

Новый тип объекта — строчка в YAML, а не ветка в коде симулятора. Это критично, если контент генерируется промптом: модель добавляет данные, а не пишет логику.

**Упор в стену — игровое событие, а не ошибка Python.** `hero.move_right()` в стену пишет `{"type":"blocked","into":"wall"}`, рендер рисует короткий тычок, в логе появляется «Тут стена, пройти нельзя». Ход при этом **тратится**, как и любое действие: мир не замирает из-за того, что герой ошибся направлением, — враги подходят, время идёт. Иначе стук в стену стал бы бесплатной кнопкой «остановить мир».

**Ворота и `hero.wait()`.** `wait` — постоять один ход: событие `wait`, один тик, герой на месте. Ворота (`waits_to_open: N`) открываются, если герой простоит на соседней клетке `N` ходов подряд, и остаются открытыми. Любой шаг, даже неудачный в стену, сбивает счёт — иначе стук в ворота заменял бы `wait`, и команда была бы не нужна. В каждый снимок мира ворота уезжают в `tiles` со счётчиком `left` — сколько ходов ещё постоять; это число ребёнок видит на воротах и по нему считает, сколько раз написать `wait`.

**Глаголы конкретные, реализация общая.** `hero.take()`, `hero.open()`, `hero.pull()` вместо универсального `hero.use()`. Внутри один обработчик, который смотрит в список `interactive` и объясняет по-человечески, если глагол не подходит.

**Радиус действия — одна клетка.** Подбираем с той, на которой стоим; взаимодействуем с соседней по направлению взгляда. Объясняется фразой «рука достаёт на шаг».

### Возвращаемые объекты — фасад, а не копия

Ребёнок обязательно напишет так:

```python
enemy = hero.nearest_enemy()
while enemy.alive:
    hero.attack(enemy)
```

Если `enemy` — копия состояния, цикл вечный. Поэтому возвращаем лёгкий фасад: внутри только `id`, а `enemy.hp` и `enemy.alive` читаются из текущего мира. Мёртвый гоблин честно отвечает `alive == False`, обращение к нему не падает.

## 6. Восприятие мира

### Читать бесплатно, действовать дорого

Запросы к миру не меняют мир и не стоят ни тиков, ни энергии. `if hero.can_move_right()` внутри цикла — ноль стоимости. Формулируется одной фразой, которую преподаватель произносит на третьем занятии: «смотреть можно сколько угодно, делать — по одному действию за ход».

### Прогрессия API

| Занятие | Что появляется | Что вынуждает написать |
|---|---|---|
| 1–2 | ничего, карта видна глазами | прямую последовательность команд |
| 3 | `hero.can_move_right()` → `True/False` | первый `if` |
| 5 | `hero.look("right")` → `"wall"`, `"goblin"`, `None` | ветвление по значению |
| 7 | `hero.nearest_enemy()` → объект или `None` | `while` с условием выхода |
| 9+ | карта генерируется случайно | код, который обязан читать мир |

Рандомизация задумывалась как защита от «вставлю условие в чат». Побочно она делает восприятие необходимым: посмотреть на карту заранее нельзя, значит захардкодить путь нельзя, значит нужен цикл с проверкой.

### Радиус обзора врага

```yaml
goblin: {sight: 3, on_spot: chase}
```

Состояние `idle` → `chasing`, события `spotted` и `lost`, «!» над врагом и подсветка зоны на карте.

**Метрика манхэттенская:** `|dx| + |dy|`, зона рисуется ромбом. Ромб в точности совпадает с числом шагов до клетки, и ребёнок проверяет это пальцем. Евклидов круг даёт «три клетки по диагонали = 4.24», режет клетки пополам и порождает вопрос, на который нет хорошего ответа.

**Стены обзор не перекрывают.** Второй закон, который нельзя проверить взглядом, делает отладку «почему он меня заметил» нерешаемой. Шов оставлен: флаг `blocks_sight` и функция `visible(from, to)`, которая сегодня всегда возвращает `True`.

**Детерминизм преследования обязателен.** Выбор между шагом по x и по y решается фиксированным правилом (сначала сокращаем большую разницу, при равенстве — x), порядок хода врагов — по возрастанию id. Иначе повторный прогон на нулевых статах даст другой результат и медали поедут.

### Туман войны

Технически добавляется флагом на уровень, но это **не регулятор сложности, а тема занятия**.

Если прятать клетки только в рендере, механики нет: код по-прежнему видит всю карту. Чтобы туман что-то значил, знание ограничивается в симуляторе — множество известных клеток, `hero.look()` за радиусом отвечает `None`, `hero.enemies()` возвращает только замеченных. Это отдельный слой состояния и отдельные события в логе.

Оправдан он ровно там, где урок звучит как «построй карту по мере исследования»: ребёнок ведёт `dict` посещённых клеток, помечает тупики, возвращается по своим следам. До такого занятия туман в бэклоге появляться не должен (правило двух школ). Шов бесплатный: весь доступ к миру из кода ученика идёт через один объект-посредник, который сегодня отвечает «известно всё».

## 7. Характеристики и экипировка

Статы и предметы не участвуют в симуляции — они участвуют во **входных данных**. Внутри уровня `loadout` не меняется: никаких «надел шлем на пятом ходу».

### Один барьер

```python
derive(loadout) -> {
    "damage": 3, "hp_max": 20, "energy_max": 10,
    "attack_ticks": 3, "move_ticks": 1
}
```

Симулятор знает только правый набор чисел и никогда не спрашивает «какая у героя сила». Добавить стат или предмет — значит поменять `derive` и `balance.yaml`, не трогая боевую логику.

| Стат | Влияет на | Причину провала лечит |
|---|---|---|
| Сила | `damage` | не убил |
| Ловкость | `attack_ticks` | не успел добить |
| Выносливость | `energy_max` | замер посреди боя |

### Только целые числа

`+2 к урону`, а не `+15%`. Причина не в балансе, а в детерминизме: дробь тянет за собой округление, а два разных места округления в браузере и в CI дают разный `checksum` и красную сборку без внятной причины. Побочно целые числа позволяют ребёнку самому посчитать, хватит ли урона на гоблина с 8 HP.

### Проверка на сервере не делается

Монеты не конвертируются в деньги, доната нет, преподаватель видит код. Читерство вредит одному ребёнку и никому больше; серверное исполнение стоит в списке «не строим». Шов открыт: тот же симулятор при необходимости запускается серверно и сравнивает `checksum`.

## 8. Персонаж и рендер

### Скелет — данные

```yaml
skeleton:
  joints:
    hip:      {x: 0,   y: 0}
    shoulder: {x: 1.5, y: -19}
    hand:     {parent: shoulder, y: 12}
    head:     {x: 1,   y: -30}
    back:     {x: -6,  y: -20}
  slots:
    weapon: hand
    helmet: head
    armor:  torso
    boots:  [leg_l, leg_r]
    cape:   back
```

Предмет объявляет только слот. Ни один предмет не содержит координат.

### Позы — тоже данные

```yaml
actions:
  attack:
    dur: 500
    keys:
      - {p: 0,    arm_front: 8,   lean: 0}
      - {p: 0.35, arm_front: -72, lean: -4}   # замах
      - {p: 0.55, arm_front: 58,  lean: 5}    # удар
      - {p: 1,    arm_front: 8,   lean: 0}
  walk:
    dur: 850
    driver: sin
    amp: {leg: 26, arm: 20, cape: 9, bob: 0.8}
```

Новое действие — блок в YAML, а не функция в коде.

### Правило, на котором всё держится

**Позиция — чистая функция от времени.** Никаких `animate()`, CSS-`transition` и очередей твинов. Каждый кадр браузера рендер спрашивает: какое сейчас время, какое событие ему соответствует, где я внутри него по прогрессу.

Нарушение ломает ровно то, ради чего затевалась плёнка: перемотка назад запускает анимации поверх текущих, ускорение 4× копит очередь, прыжок ползунком оставляет персонажа где попало.

### Два уровня трансформаций

- **Внешняя группа — положение**, ставит JS из интерполяции. Только `translate`, никакого пересчёта layout.
- **Внутренние группы — суставы**, фаза шага и замаха, тоже функция от прогресса.

Предмет рисуется **внутри группы своего якоря** — как `<image>` в SVG: сапог попадает в группу ноги и поворачивается с ней бесплатно, меч — в группу руки. Анимации атаки для меча и для топора не существует по отдельности: крутится плечо, оружие висит на кисти.

### Порядок слоёв фиксирован

```
плащ → задняя рука → ноги с сапогами → тело → доспех
→ голова → шлем → передняя рука → оружие
```

Предмет не выбирает свой слой. Следствие: **доспех рисуется поверх тела, а не заменяет его**. Мантия — фигура, накрывающая торс, а не новый торс, иначе появятся комбинации, где тело исчезло, а руки остались.

### Длительности — данные

```yaml
timings:
  move: 450
  attack: 500
  damage_flash: 150
  death: 300
  speeds: [1, 2, 4]
```

Скорость 2× — это деление времени на два, никаких изменений в рендере. Пропуск анимации (для повторного прогона на нулевых статах) — отрисовка последнего кадра.

Тик мира и длительность анимации связаны этой таблицей, а не формулой «1 тик = 200 мс»: иначе мгновенные действия выглядят как зависание, а долгие пролетают незаметно. Внутри одного тика у событий разные окна (герой 0–60%, враги 40–100%), иначе всё дёргается синхронно.

### Ограничения рендера

- **Клетка 80 px, тело героя ~60 px** (три четверти клетки). Оставшаяся четверть — запас под предметы: рога шлема и поднятый меч не должны заезжать на соседние клетки. Ассеты рисуются в 2× (160 px на клетку в исходнике), чтобы на ретине край был чётким. Сцена — SVG, поэтому 80 — номинал, под который рисуется графика, а не жёсткий размер на экране: на маленьком ноутбуке карта сжимается целиком, на мониторе — растёт.
- **Два направления, не четыре.** Вид сбоку, поворот через `scale(-1, 1)`. Движение вверх и вниз использует тот же вид. Асимметричные детали (шрам, повязка на глаз) поэтому не делаем.
- **Слои.** Статичная карта перерисовывается редко; герой, враги, цифры урона — каждый кадр. Двадцать элементов на `requestAnimationFrame` — нагрузка, которой не существует.

### Персонажи: один риг, разные части

Персонаж — это не одна картинка, а **набор частей на стандартных холстах**: голова, торс, передняя рука, задняя рука, нога. Рендер кладёт каждую часть в группу своего сустава — ровно так же, как предмет. Позы из YAML работают для всех персонажей сразу, ничего не перерисовывается покадрово.

Отсюда правило, которое нельзя нарушать: **у всех персонажей одинаковые пропорции.** Голова одного размера, руки и ноги одной длины, торс одной высоты. Разница — лицо, кожа, волосы, одежда под доспехом. Гном в полтора раза шире рыцаря невозможен: на него не сядет шлем, и габаритный прямоугольник поедет. Персонаж — это визуальный выбор, физически все занимают одно место.

## 9. Предметы: картинки на скелете

Предмет — это PNG, нарисованный ИИ, плюс параметры. Фигуру не собирает рендер и не рисует человек: картинку генерирует модель по промпту с эталонным персонажем как референсом, скрипт обрезает и кладёт в атлас. Как именно — в [generatsiya-grafiki.md](generatsiya-grafiki.md).

```yaml
- id: forest_glaive
  name: Лесная глефа
  slot: weapon
  rarity: редкая
  price: 270
  mods: {damage: +3, energy_max: +3}
  image: weapon/forest_glaive.png
  offset: {x: 0, y: -2}
  silhouette: изогнутое лезвие на древке
```

### Холст слота вместо координат

Предмет объявляет слот, а холст слота задаёт всё остальное: размер и **точку крепления** — где на картинке находится сустав. Все шлемы рисуются на одном холсте, где макушка головы в известной точке; всё оружие — на холсте, где кисть на известной высоте рукояти. Художник (модель) рисует на шаблоне, рендер кладёт картинку в группу сустава со сдвигом до точки крепления.

`offset` — единственные координаты в предмете, и это не координаты фигуры, а поправка точки крепления в пикселях. ИИ не умеет класть рукоять ровно в заданный пиксель; правило слота даёт точку по умолчанию, гардеробная позволяет подвинуть мышкой и сохраняет результат. Два числа, не путь.

### Три запрета

1. **Своя анимация у предмета.** Убивает свойство «новый предмет получает анимацию бесплатно». Меч крутится потому, что крутится плечо; особые действия принадлежат скелету.
2. **Свой порядок слоёв у предмета.** Стек фиксирован, предмет попадает в свой слой и не спорит. Доспех — поверх тела, не вместо него.
3. **Свои пропорции у предмета.** Картинка рисуется под эталонного персонажа и на холст слота. Шлем «чуть больше, чтобы было видно», не проходит габарит и не попадает в игру.

### Что растр отнимает

Честно, чтобы не удивляться потом:

- **Цвет предмета — не токен.** У картинки цвета зашиты. Тёмная тема перекрашивает интерфейс и карту, а не доспехи. Токены остаются для всего, что рисуется кодом: пол, интерфейс, цифры урона, полосы здоровья.
- **Комбинаторики нет.** Раньше 14 кусков кода давали 600 мечей; теперь каждый предмет — отдельная генерация и отбор глазами. 50–80 предметов на учебный год — посильный объём, тысяча — нет. Предметов становится столько, скольким дали имя и картинку.
- **Стиль держится референсом, а не кодом.** Первый принятый персонаж — эталон, и он прикладывается к каждому промпту. Заменить эталон — значит перегенерировать всё.

### Гардеробная в CI

Не изменилась по смыслу и упростилась по реализации: у растра прямоугольник непрозрачных пикселей считается тривиально. Страница рендерит декартово произведение персонажей и слотов, автоматика проверяет, что каждая комбинация отрисовалась и попала в габарит (рог не уехал за клетку, меч не проткнул голову). Красоту смотрит человек, раз в спринт. Конфликты лечатся строкой `incompatible_with: [hood]`.

Гардеробная же — место, где выставляется `offset`: перетащить, сохранить в YAML.

### Промпт генерации данных предмета

Картинку и параметры генерируют разные промпты. Этот — про параметры: имя, цену, `mods`, описание силуэта, которое потом уходит в промпт картинки. Меняются три строки сверху: редкость, слот, стиль.

```
РЕДКОСТЬ: редкая
СЛОТ: weapon
СТИЛЬ: лесной
---
Ты генерируешь предметы для 2D-игры. Картинку нарисует другая модель
по полю silhouette, поэтому оно должно быть конкретным и коротким.

СТИЛИ:
  рыцарский    — сталь, бронза, прямые формы, кресты и заклёпки
  лесной       — кожа, дерево, изогнутые лезвия, капюшоны, зелень
  механический — шестерни, зазубрины, тёмный металл
  восточный    — изогнутые клинки, золото, ткань, узор

РЕДКОСТЬ (задаёт бюджет, не внешность):
  обычная      60–120    сумма mods 1–2
  необычная   130–220    сумма mods 3–4
  редкая      230–350    сумма mods 5–6
  легендарная 360–500    сумма mods 7–8

MODS: целые, из набора damage (+1..+4), hp_max (+2..+8),
energy_max (+2..+6), attack_ticks (-1 или 0).
attack_ticks -1 считается за 3 единицы бюджета.
Цена = сумма единиц × 45, округлить до десятков.

ПРАВИЛА:
- silhouette: 3–8 слов, форма и материал, без прилагательных-оценок
- все предметы в ответе — с разными silhouette
- предмет читается на 60 пикселях: одна главная деталь, не три
- название русское, 1–2 слова, без эпитетов «могучий», «древний»
- ответ YAML, без пояснений и markdown-обёртки

ЗАДАЧА: сгенерируй 8 предметов указанных слота, редкости и стиля.
```

Редкость влияет на бюджет, но не на форму: иначе легендарные предметы станут отдельным визуальным классом.

## 10. Защита от бесконечности и ошибок

**Бюджет вместо зависания.** `sys.settrace` считает выполненные строки: 50 000 — стоп с сообщением «твой код работал слишком долго, скорее всего цикл не заканчивается». Отдельный лимит на тики мира. Ребёнок никогда не видит замершую вкладку.

**Медали считаются, а не оцениваются.**
`ast_nodes` — размер AST, а не число строк: иначе дети сожмут всё в одну строку через `;`.
`repeats` — нормализуем поддеревья AST, хэшируем, ищем повторяющиеся последовательности из двух и более соседних инструкций. Четыре скопированных `hero.move_right()` — повтор, медали «чисто» нет.

**Песочница.** Код ученика исполняется в отдельном namespace, мир виден только через фасад с read-only свойствами. Идеальной изоляции не будет и не требуется.

**Ошибки Python переводятся в человеческие.** Отдельная таблица соответствий (`NameError` → «ты используешь имя, которое ещё не создал»), часть контентного конвейера, а не кода.

**Вертикальный срез (≈2 недели).** Один уровень, четыре команды, движение без боя, плеер с шагом назад, загрузка из YAML, pytest на симулятор.

## 13. Технические «не строим»

В дополнение к списку из общей идеи:

- Серверное исполнение кода и серверная валидация прохождений
- Игровой движок (Phaser, Pixi) — SVG достаточно
- Покадровые спрайты персонажа — только риг из частей, иначе каждый предмет придётся рисовать на каждый кадр
- Разные пропорции у персонажей
- Четыре направления персонажа
- Дробные модификаторы и проценты
- Императивные анимации и твин-библиотеки
- Diff-кодирование кадров
- Второй интерпретатор для «быстрого режима»
